# research.md — Glyph Grid Studio v0.2: second-pass performance audit + SOTA feature research
**Date:** 2026-10-17 · **Baseline:** v0.1.10 (`main` @ 24c4d68, ITER-040..044 landed today) · **Branch:** `audit/v0.2-sota`
**Method:** 5 dimension auditors (headless throttling, GPU render core, encode/export, startup/UI/memory, CLI/MCP/batch), each finding re-verified by an independent skeptic that tried to refute it against the source; 3 feature ideators (creator workflow, rendering research, agent ecosystem) × 5 features, scored by 2 judges (product, engineering). 40 agents, 470 tool calls. Every claim below cites `file:line`; estimates are labelled UNCERTAIN where the skeptic could not measure.
**Verdict:** 27 findings confirmed · 3 debunked · 15 feature proposals (13 unique) ranked.

## 0. The headline that changes the plan
Today's v0.1.10 work was planned on the model *"headless render is idle: 2.7 s CPU vs 20–56 s wall, WebKit throttles the off-screen window"*. **That model was wrong.** `time`/rusage only sees the Tauri process; WebKit's `WebContent.xpc` and `GPU.xpc` are launchd children (ppid 1) and were never counted. Direct sampling (finding #1) shows ~18 s of XPC CPU on a 13.5 s wall render, with the **GPU process dominant (88–212 % CPU)**. The main thread is saturated, not throttled — and 40 % of its samples sit in the synchronous `canvas.toBlob` readback wait (finding #2). The earlier 'debunked' entry *CPU under-count in XPC* had no written evidence behind it and is reinstated as real.
Consequences: (a) every headless number recorded so far must be re-baselined with an XPC-aware sampler before any further capture work; (b) the next levers are the readback path and GPU-process canvas IPC, not rAF cadence; (c) output is not yet a pure function of (source, config, seed) — the EMA warm-up depends on how many live draws ran before frame 0 (finding #23), which is why #20 was reverted and why PSNR gates show 36–38 dB self-noise. Determinism has to land before any GPU/WebGL path can be gated.

### R1 · Parameter timeline: keyframes on any CONFIG path (and finally wiring paletteMorph) · effort M · score 32.5

**Pitch.** Keyframe any slider — palette, cols, gamma, breathing, CRT strength — over the loop with eased interpolation, scrub it on a timeline, and drive the same curves from the CLI/MCP with Deforum-style `0:(0.2), 0.5:(0.8)` strings. Palettes morph in OKLab between keyframes, which is what `CONFIG.paletteMorph` promised and never delivered.

**Why SOTA.** Today an animation is 'one look, breathing' plus one hard-coded special case (dispersal's startT→endT). Creators want reveals (cols 60→240), palette drifts, CRT fade-ins timed to a drop. A generic keyframe track over the existing deep-merge config system is cheap and unlocks every future feature (audio mappings, text timing) as 'just another track'. **What exists already.** `src/index.html:266 paletteMorph: null` is declared and gated (`src/lib/glyph-compat.js:99-102 function gatePaletteMorph(config) { ... return !!(config.paletteMorph && config.paletteMorph.enabled); }`) and listed as pipeline step '7. The studio's colour story is palette-driven and raster-only: 11 hand-authored palettes, `preserve` uses the raw per-cell mean (`sampleCell`, index.html:1800-1812) with no quantisation, and the only quantiser in the codebase runs at GIF encode (gifski in lib.rs; `gifenc.quantize(f.data, 256)` in glyph-outputs.js:251). Doing the quantisation in OKLab at the cell stage, with error diffusion, is what makes limited-palette output look intentional rather than posterised — and it is what lets a render leave the app as text that is pixel-equivalent in any truecolor terminal.

**What exists already.** PALETTES table (index.html ~345-400, includes kawaii-pink); OKLab/OKLCH maths (glyph-palette-morph.js:23+) and gradient LUT `_ensureGradColorLut` (index.html:4149); scalar error-diffusion kernels FS/Atkinson/JJN (glyph-dither.js:213-266, single channel only); `ansi16` palette only inside the runtime DSL (glyph-polish.js:25) — not reachable from the studio; TXT export (glyph-studio.js:1930-1933) but no ANSI: grep for \x1b / escape sequences in src/ returns 0 hits; 64x64 cached probe for the invert suggestion (ITER-043) is the right downsample pattern to reuse.

**Design.** (a) Extraction: on source load, when `CONFIG.palette === 'auto'`, downsample to 128x128 (reuse the ITER-043 scratch-canvas probe), convert to OKLab, run k-means++ (seeded from CONFIG.seed, fixed 12 iterations, K = `paletteK` 3-8), sort stops by L, choose bg as the lightest or darkest stop per `invertSignal`, optional OKLCH chroma boost; materialise the result as explicit hex in CONFIG so presets, CLI and MCP renders stay deterministic. (b) `colorMode: 'quantized'`: per cell nearest ink in OKLab (K ≤ 256, brute force) with optional 3-channel error diffusion — generalise `applyErrorDiffusion` to an interleaved Float32 RGB buffer, same kernels. Targets: active palette | ansi16 | ansi256 | xterm 6x6x6 cube. (c) `Export ANSI`: extend captureGridSnapshot's cell list (col,row,c,f,o) into runs of equal fg, emit `\x1b[38;2;r;g;bm` (truecolor) or `\x1b[38;5;Nm` (256), `\x1b[0m\n` per row, optional bg via 48;2; save as .ans/.txt through `save_blob`. UI: Color folder → palette 'auto', `paletteK`, `Extract palette` button, `quantize target`. CLI: `--palette auto --palette-k 5 --color-mode quantized --quantize-target ansi256`, `--format ans` (format already exists in RenderArgs, main.rs:106); MCP: `format` enum extended, `palette_k`. Catalog lists `auto` and the targets.

**Risks.** k-means on muted photos yields muddy inks — mitigated by chroma boost and by always offering the hand palettes. Terminal cell aspect: default cells are ~4.27 px wide × 8.5 px tall (240x120 on 1024x1024) while terminals are ~1:2 per character, so the ANSI/TXT exporter should offer a 'terminal fit' resample (cols:rows ≈ 2:1 grid) or document the mismatch. Naive per-cell escape codes for 28,800 cells approach 600 KB — run-length merging is required. Vector error diffusion is serial (same as existing ED modes) — CPU only, fine at 240x120.

**Prior art.** chafa (Hans Petter Jansson) — colour quantisation + dithering to terminal colour models; ascii-image-converter (TheZoraiz); libcaca (export to ANSI/HTML/SVG); Björn Ottosson, OKLab (2020); Arthur & Vassilvitskii, 'k-means++', SODA 2007; Floyd & Steinberg 1976; the ANSI art scene .ans format.

### R15 · `@lovespark/glyph-grid-core`: a p5-free grid solver published as an npm library, powering an in-browser landing-page demo and a thin Python wrapper · effort XL · score 20.0

**Pitch.** Extract the deterministic 'image → cell grid of {glyph, rgb, alpha}' solver out of index.html into a dependency-free ESM/UMD module that the Tauri app, Node scripts, the website demo and a `pip install glyph-grid` wrapper all share. Rendering to canvas/text/SVG/ANSI becomes a set of small renderers over one data structure — the grid becomes the API.

**Why SOTA.** The best-in-class reference implementations (chafa as a C library + CLI, Harri's shape-vector article) are libraries first. Today the solver is welded to p5 globals and the WKWebView, so nobody can embed it, unit-test it in CI, or try it on the website; the landing page shows pre-rendered GIFs only (docs/index.html:389-447 is theme-toggle + copy-button JS, no canvas). A library that runs in Node makes 'render in CI' trivial (no Tauri, no off-screen WebKit throttling for text/SVG outputs) and is the honest path to a web demo — far cheaper than a WASM port of a renderer that does not exist in Rust (src-tauri only holds encoders and IPC: lib.rs fn index shows gifski/openh264/mp4 + Tauri commands, no rasterizer).

**What exists already.** A registry/pipeline skeleton exists: `GlyphGrid.runtime.register/pipeline/run` with the axis order source→transform→sampling→selection→color→composition→postProcess→output (src/lib/glyph-runtime.js:1-60) and primitives in glyph-primitives.js, glyph-sampling.js, glyph-outputs.js (including `output.svg` at glyph-outputs.js:149-195). All src/lib files are IIFEs attached to `window.GlyphGrid` and already load in Node via `vm` (tests/frontend-contracts.test.js:1-12). But the production hot path is in index.html: `drawBrightnessGrid`/`drawShapeGrid`, the gamma LUT (`_buildGammaLut`), gradient LUT (`_ensureGradColorLut`), `sampleCellInto`, and `captureGridSnapshot` (index.html:4112-4213) all use p5 globals (`color()`, `red()`, `width`, `height`, `src.pixels`). The shape/k-d tree code is already separable (src/lib/glyph-shape-index.js, 541 lines). No npm publish config (package.json is `"private": true`), no Python package, no WASM. Cargo.toml declares `crate-type = ["staticlib","cdylib","rlib"]` but `app_lib` is Tauri-bound, not an embeddable renderer.

**Design.** Files: new `src/core/` ESM sources — `solve.js` (`solveGrid(image:{data,width,height}, config, state?) → Grid {cols,rows,cellW,cellH,glyph:Int16Array,rgb:Uint8Array,alpha:Float32Array,ramp,palette}`), `animate.js` (seeded, explicit-step `Animator` holding EMA/breathing/jitter/temporalStability state so output is deterministic by `(seed, frameIdx)`), `palette.js` (port of the p5 `color()` uses to a tiny hex/rgb parser), re-exports of glyph-shape-index/glyph-dither/glyph-palette-morph; renderers `render/canvas.js` (atlas blit, used by the app), `render/text.js` (txt/ansi/cast/html from feature 1), `render/svg.js` (moves `buildSvg`). Build: `scripts/build-core.mjs` using esbuild (dev dependency only) → `dist/glyph-grid-core.{esm,umd}.js`; package `@lovespark/glyph-grid-core` (MIT, zero runtime deps). App integration: index.html's `captureGridSnapshot` and the brightness draw path call `solveGrid` and keep only typesetting; gate with the existing PSNR/byte-parity harness (tests/run-all.sh Phase F) so GIF output is unchanged. Web demo: docs/demo.html (and a block on docs/index.html) with a drop zone + 6 preset buttons rendering live on a `<canvas>` via the UMD build; static, no server, respects `prefers-reduced-motion`. CLI: `glyph-grid-studio render --format txt|svg|ansi` can bypass Tauri entirely by running the core in Node when available (optional fast path, UNCERTAIN gain; the WebView path remains canonical for GIF/MP4). Python: `python/glyph_grid/` wrapping the CLI via `subprocess` with NDJSON progress (feature 3) and a `Grid` dataclass parsed from `--format json`; publish to PyPI; no paid API anywhere.

**Risks.** Output drift is the central risk: p5 `color()` parsing, `Math.floor` vs `|0`, and EMA warm-up ordering (the deferred #20 note: fewer warm-up draws changed EMA state) must be reproduced exactly; require byte-identical GIFs on the regression corpus before switching the app over. Shape/edge modes depend on the pre-baked atlas JSONs in src/glyph-sets/ — the npm package must ship them (size UNCERTAIN; check `du -sh src/glyph-sets`). The CRT postprocess chain (glyph-crt.js, 717 lines) operates on RGBA buffers and is already separable, but keep it out of the core v1 to limit scope. Maintaining two consumers (app + package) invites forks — enforce a single source by having the app import the built core, never a copy. WASM remains out of scope: there is no Rust renderer to compile, and gifski's threading complicates wasm — say so in docs rather than promise it.

**Prior art.** chafa (hpjansson) — library + CLI split for terminal graphics; p5.js instance mode / p5-free module patterns; esbuild for zero-config ESM+UMD bundles; Alex Harri, 'ASCII rendering with shape vectors' (2024, already cited in README); jp2a and image-to-ascii (npm) as smaller library precedents; Python `subprocess`-wrapper packages such as `ffmpeg-python` for the CLI-binding style.
